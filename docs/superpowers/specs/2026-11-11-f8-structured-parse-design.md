## 0. 一句话

标题带认身份并对库判矿物；body 主职品质（矿物可同带 SCU）；格子角标给 F8/F6 品质与数量回退；身份允许模糊对库，品质/数量必须专用数字解析。

---

## 1. 背景

F8（`tasks/hover.py` → `inspect_item`）与 F6 盘点共用 `trade/inspector.py`。产品上 F8 要打开物品查询、预填入库、按品质档查市价，因此结构化结果里的 **名字 / 品质 / 数量** 都重要。

此前标题带规格（2026-11-04）优化了「少送像素认物」，但未单独钉死结构化解析的职责切分。实践中容易把「对库模糊」和「数字精确」混在同一套文字处理预期里，也容易把角标当成仅 F6 或可有可无。

本文固定：**现状是什么**、**目标契约是什么**、二者差在哪。

---

## 2. 目标 / 非目标

**目标**

1. 写清 `inspect_item` 结构化阶段的通道职责与优先级（标题 / body / 角标）。
2. 写清身份对库与度量数字的双通道原则。
3. 记录验收对照；差距项在 §8 维护（已实现项标「已满足」）。

**非目标**

- 改 OCR 引擎或 PP-OCR 版本（另见 ppocr 规格）。
- 重开标题带 `TITLE_Y*` / `BODY_Y*` 数值（仍以 2026-11-04 规格为准）。
- 用 OpenCV / HSV 在 body 上做「品质色带」定位并作为本期契约（见 §7：待验证）。
- 自动把 F8 结果写入库存账（现状是物品页预填入库表单；契约不改为自动入库）。

## 3. 现状（代码事实）

入口：`astral_toolkit/trade/inspector.py` · `inspect_item`；名字纠正：`trade/names.py` · `canonical` / `canonical_exact`。

**级联（origin/dev，PR #18）**：`_read_tooltip` 只走 **标题带 → 说明框带**，不再全高竖条、不再整屏 OCR（见 2026-11-04 规格 2026-11-09 变更）。

**结构化补扫（origin/dev + Task 2）**：`inspect_item` 在 `where` 以 `@title` 结尾、且标题 tokens 尚无完整度量时，会调用 `_tooltip_body_tokens` 补扫说明框带。**非矿物**：缺品质即补扫；**矿物**：缺品质或缺 SCU（`tooltip_row` 数量）即补扫。与 §4.3「标题命中后仍必跑 body（需度量时）」一致。

### 3.1 流程摘要

```
截图 + 光标
  → _read_tooltip（标题带 → 说明框带）
  → tooltip_pick → (zh, en)
  → canonical → 标准名；sure = 是否对上库
  → _is_mineral(zh, en)          # 按名字对采矿/矿物表，不是看单位
  → tooltip_row / tooltip_quality # body 品质、矿物 SCU
  → cell_labels                   # 非矿物：左上品质角标、右上数量角标
  → 可选制造倒推（parse_mods / solve_slots）
  → 返回 {zh, en, quality, qty, unit, sure, …}
```

### 3.2 矿物

`_is_mineral`：**只看名字**（信号表 / 矿物汉化），`fuzzy` 在已 `canon` 时关闭。  
`unit="SCU"` / 用 `tooltip_row` 的量，是矿物判定**之后**的结果，不是判定输入。

### 3.3 品质来源（现状合并）

优先级大致为：

1. 说明框内容行 / 「品质：」字段（`tooltip_row` / `tooltip_quality`）
2. 格子左上角 `575Q`（`parse_qlabel`）
3. 制造倒推（F8 默认仅在未读到数字时；F6 可用 `craft_override`）
4. 非矿物仍无则默认 `0`；矿物无默认品质则为 `None`

### 3.4 数量来源（现状）

- 矿物：`tooltip_row` 的 SCU 量  
- 非矿物：角标 `200x`（`parse_count`），缺省按 `1` 个  

### 3.5 身份对库（现状）

`canonical`：折叠（`fold_en` / `norm_zh`）、英文 `l↔i`、英文/中文模糊比、矿名差一字等。  
标题带早停用 `canonical_exact`（不做模糊），见 2026-11-04 §4。

### 3.6 与产品下游

- F8：`hover_once` 用本机卡片上屏；`_hover_more` 按品质档查市价；窗口物品页可预填入库（**手动确认**）。  
- F6：会话累加后对账，`count_apply` 才写库存。

## 4. 目标契约（结构化解析）

### 4.1 三通道职责

| 通道 | 职责 |
|---|---|
| **标题带** | 物品身份；对库后判定是否矿物（**不看**数量单位） |
| **body（说明框带）** | **主职品质**；对矿物**额外**允许同带解析 SCU 量；制造倒推所需加成行也在 body tokens |
| **格子角标** | F8 与 F6 **共用**：左上品质、右上堆叠数量 |

### 4.2 优先级

- **品质**：body 优先；角标仅回退。body 与角标不一致时听 body。  
- **非矿物数量**：角标 `Nx`；无则按 `1` 个（与现状一致，契约不改为省略数量）。  
- **矿物数量**：body 内容行 SCU；角标 `Nx` 一般不是矿物 SCU 量。

### 4.3 路径要求

1. **标题库命中后仍必跑 body**（需要品质或矿物量时）：身份可在标题带定下，但不能因此跳过 body 度量。制造品无数字品质时，倒推仍走 body（标题命中后若无加成行，按现有逻辑补裁 body）。  
2. **无说明框降级路径**：允许「名字能对库 + 角标品质/数量」出结果（说明框未弹出就按 F8）；应可区分完整路径与降级（日志 / `where` / sure 语义保持可读）。  
3. **非矿物完全无品质**：默认 `quality=0`（市价按 q0；与现状一致）。

### 4.4 F8 与入库 / 市价

F8 需要品质与数量，因为：

- 物品页入库表单预填；  
- 玩家市场按品质档（q0–q7）查价。  

契约**不**要求 F8 热键直接 `apply` 库存；写账仍经用户确认（或 F6 对账确认）。

## 5. 双通道文字原则（硬原则）

OCR `tokens` 之后必须分成两条处理哲学，禁止混用：

| 通道 | 成功标准 | 允许 | 禁止 |
|---|---|---|---|
| **身份** | 对上汉化包 / 矿物表，返回标准名 | 折叠、模糊、形近、丢字容忍（`canonical` 档位）；标题早停用 exact | 用「猜数字」当认物成功条件 |
| **度量**（品质、堆叠、SCU） | 解析出可用数字 | 专用解析器与已知 OCR 数字坑（如 `907Q`→`9070`） | 用 `canonical` 式模糊去猜品质/数量 |

说明：英文物品名可以含数字（型号等），`fold_en` 保留 `0-9` 作比较键。身份侧「不精确」指 **OCR 糊了仍可靠库对齐**，不是「名字里的数字一律丢弃」。

实现落点（现状已基本分开，契约要求保持）：

- 身份：`names.canonical*`、`tooltip_pick`  
- 度量：`tooltip_row` / `tooltip_quality` / `parse_qlabel` / `parse_count`

## 7. 非目标：颜色 / OpenCV「品质带」（待验证）

**假设（未证实）**：说明框或角标上的品质数字带有稳定、可分割的颜色，可用 OpenCV 高亮 / 定位后裁「品质带」再 OCR，以提高速度与数字精度。

**公开资料**：官方与 Wiki 只保证品质为 0–1000 数值及出现界面（采矿 / 库存 / 制造）；**未**文档化说明框品质的固定色相。本仓库 F8 路径亦无颜色定位。

**验证门槛（通过后才可另开规格改契约）**

1. 在真实截图样本上统计品质数字区域相对周围 UI 的 HSV/亮度可分性（多分辨率、明暗、中英界面）。  
2. 误检率：不得把「体积 / 制造商 / 锚点行」稳定裁成品质带。  
3. 相对现有「body 文本解析 + 角标小裁 `native`」的中位耗时与错题不恶化。  

未满足前：**不得**把颜色品质带写进实现硬路径。
